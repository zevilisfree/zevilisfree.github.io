聊天分支（Fork）與工作樹（Worktree）隔離

掌握 Fork + Worktree A/B 雙軌實作、environment.toml 初始化腳本、.worktreeinclude 與 Hand off 三種衝突處理模式。

什麼時候開新對話、什麼時候建立分支（Fork）

一則聊天處理一個明確的結果。當出現兩個獨立方向時，可以開兩則聊天平行處理，不必把所有要求都塞進同一個對話裡。

點擊左上角側邊欄的「新對話」按鈕適合完全獨立的新任務；而分支至新對話（Fork，或在對話框輸入 /fork）則適合「已經討論並釐清了一段專案背景或規劃（/plan），想從這個時間點分出兩條路線各自推進」。

從某則訊息建立聊天分支（分支至新對話，/fork）與 A/B 雙軌對決技巧

  1. 找到希望保留的那段上下文

    回到一則已經完成的回答末尾，點擊下方的「⋯」更多動作按鈕並選擇「分支至新對話」（或在輸入框輸入 /fork）。選擇哪一則回答，就決定了從哪個時間點複製上下文推進。

  2. 選擇分支的執行環境（本機 Local vs. 新工作樹 Worktree）

    點擊後，依需求選擇「在此工作空間中建立分支（/local）」，或針對 Git 專案選擇「在新工作樹中建立分支（/worktree）」。

  3. 在新對話中繼續（或進行 A/B 方案平行對決）

    開啟新出現的聊天，檢查保留下來的上下文，再發送新的要求。

新聊天會保留分支點之前的對話上下文；分支點之後在原聊天新增的訊息，不會自動同步到新分支。所有對話都可以重新命名（從聊天選單選擇「重新命名」或輸入 /rename），建議將分支聊天命名為清楚的方案名稱（如「重構方案 A：Context API」與「重構方案 B：Zustand」）。

💡 實戰進階組合技：/plan → Fork 雙工作樹 A/B 方案平行對決

當團隊或你自己對兩種技術做法猶豫不決時，千萬不要在同一個資料夾裡改了又拆。最佳實戰流程是：① 先在主對話用 /plan 讓 Codex 盤點現有程式碼並列出共通需求；② 在該則規劃回覆末尾按兩次 Fork，並都選擇「在新工作樹中建立分支（Worktree）」；③ 讓分支 A 與分支 B 同時在兩個完全隔離的 Git Worktree 中平行實作並跑測試；④ 對照兩邊 Review 面板的程式碼複雜度與測試結果，將勝出的那一個分支透過 移交（Hand off） 合併回本機主工作區！

聊天獨立，檔案未必獨立（三種平行隔離層次）

請特別注意：聊天分支（Chat Fork）不等於 Git 分支！如果在分支時選擇「在此工作空間中建立分支（Local）」，兩則聊天仍然會同時讀寫你電腦上的同一個資料夾。一邊修改檔案，另一邊就會讀到或覆蓋這些變動。為了避免平行工作時發生踩踏衝突，請依情境選擇三種隔離層次：

  • 層次 1：同資料夾讀寫分工（Local，Free / Plus 皆可用）：一則聊天只負責唯讀分析與查文件（或使用 /side 支線聊天），另一則負責實際修改；若兩則都要改檔案，必須事先嚴格界定各自負責的子目錄。
  • 層次 2：本機 Git 工作樹隔離（Worktree，/worktree，Free / Plus 皆內建）：Codex 會在 $CODEX_HOME/worktrees 下建立獨立的 Git 工作樹副本（可選擇起始分支 Starting branch，並自動帶入未暫存變更）。不同聊天在各自的 Worktree 目錄中平行改 Code、跑測試，彼此 100% 互不覆蓋。
  • 層次 3：Codex 雲端任務平行沙盒（Cloud，Plus 以上可用）：針對已連結 GitHub 的儲存庫，輸入 /cloud 將任務丟上 OpenAI 託管的雲端隔離容器執行，不佔用本機 CPU 與磁碟，關機也能繼續跑。
雲端環境依帳號目前顯示的資源選擇

雲端任務的可用性與資源規格依方案、工作區及設定不同。建立前查看當前畫面，不以舊截圖推定固定記憶體容量。

工作樹（Worktree）初始化腳本、.worktreeinclude 與移交（Hand off）三種衝突處理

在桌面版使用本機 Git 工作樹（Worktree）平行開發時，有三個決定成敗的關鍵細節（詳見 官方 Git Worktrees 指南）：

  1. 設定本機環境初始化腳本（Setup Script / environment.toml），解決新工作樹缺套件問題：

    新建立的 Git Worktree 只包含受 Git 版本控制的原始碼，預設不會有 node_modules/、Python 虛擬環境或編譯快取，常導致代理一進 Worktree 跑測試就報錯。你可以在專案的本機環境設定中配置 Setup Script（或寫入儲存庫的 .codex/environments/environment.toml，支援針對 Windows、macOS、Linux 分別定義安裝指令），讓 Codex 每次建立新 Worktree 時自動執行 pnpm install 或環境初始化。

  2. 用 .worktreeinclude 自動複製被 .gitignore 忽略的非敏感本機設定檔：

    已被 .gitignore 忽略的本機開發設定檔預設不會進入新工作樹。若測試必須使用某個非敏感的本地設定檔，可在專案根目錄建立 .worktreeinclude（支援與 .gitignore 相同的 glob 萬用字元語法），Codex 建立新 Worktree 時就會自動將匹配檔案複製過去。資安鐵則：切勿將含有真實生產環境金鑰、Token 或客戶個資的檔案公開貼入教學或版本控制中。

  3. 在本機（Local）與工作樹（Worktree）間移交（Hand off）與三種衝突解決策略：
    • 點擊聊天標題列的「在此建立分支（Create branch here）」，可將處於 Detached HEAD 狀態的工作樹轉為正式 Git 分支並直接 Commit / Push。
    • 當你想把 Worktree 的成果帶回本機 IDE 實測（Hand off to Local），或把本機做到一半的工作移交到背景工作樹（Hand off to Worktree）時，若系統偵測到本機與工作樹雙邊都有未提交變更或檔案衝突，會提供三種狀態轉移模式供你選擇：
      • Apply（套用差異修補）：將來源端的變更以 Patch 方式套用到目標端，適合兩邊修改不同區塊、希望融合變更時使用。
      • Overwrite（強制覆寫目標）：直接以來源端的完整狀態覆蓋目標端工作目錄。注意：目標端未提交的獨立修改會被覆蓋，點選前務必確認！
      • Keep both（保留雙邊版本）：同時保留兩邊的變更或衝突標記，讓你後續手動檢視與合併，是最安全的保底選項。

工作樹（Worktree）自動快照（Snapshot）與永久工作樹（Permanent worktree）

Codex 預設在 $CODEX_HOME/worktrees 保留最近 15 個受管工作樹（可於「設定 → Worktrees」調整上限）。當聊天被封存或超過數量上限時，系統會先自動儲存一份快照（Snapshot）再清理磁碟空間，日後重新打開該則聊天即可一鍵還原；若你需要一個長期保留、不被自動清理且可供多則聊天共用的隔離目錄，可從專案選單建立「永久工作樹（Permanent worktree）」。
